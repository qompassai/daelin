# Chapter 5 — A2A: How Agents Talk to Agents

*Implementation: Diver `lua/ai/a2a/` (init, agent_card, client, tasks,
orchestrator, fanout, sdks, ui, commands). Pair with chapter 1's timeline.*

## The idea in one paragraph

MCP connects an agent *down* to tools. A2A connects an agent *sideways* to
another agent. The scenario: your planner agent needs a code review, and
there's a reviewer agent running somewhere else — different machine, different
framework, different vendor. A2A is the protocol where your agent discovers
that reviewer, learns what it can do, sends it a task, and gets back artifacts.
Neither agent needs to know the other's internals; the protocol is the
contract.

## The Agent Card: discovery without trust

Everything starts with the **Agent Card** — a JSON document at the well-known
URI `/.well-known/agent-card.json` that says: who I am, where to reach me
(the JSON-RPC endpoint), what I can do (skills), and how to authenticate.

The implementation (`agent_card.lua`) treats cards with the correct posture:

- **Cards are validated** against required fields on fetch. A malformed card
  is rejected, not tolerated — tolerant parsers are how confusion attacks
  enter.
- **Cards are fetched with bounds**: 256 KiB max, 10s timeout. A discovery
  document is untrusted network input; unbounded fetches are DoS vectors.
- **Cards are never executed; only their resolved endpoint URL is used** —
  and only after the client's scheme/host checks pass. The card tells you
  *where* the agent is, not *what* to do. This is the same "data vs.
  instruction" separation as chapter 4's tool descriptions.

Since v0.3.0 (and mandatory in the v1.0 stable spec), cards can be
**signed** — cryptographic attestation that the card actually came from who
it claims. Unsigned cards are self-asserted identity; signed cards are
verifiable identity. The implementation checks signatures where present.

## The task lifecycle

A2A's unit of work is the **task**:

1. **Send** — the client POSTs a task request (JSON-RPC) to the agent's
   endpoint: what to do, in what form (messages with *parts* — text, files,
   structured data; modality-agnostic by design).
2. **Track** — the task has a lifecycle (submitted → working → completed /
   failed). Long-running tasks are first-class: the protocol was designed for
   work that takes minutes, not milliseconds.
3. **Receive** — the agent returns **artifacts**: the outputs of the work, as
   typed parts. Messages carry the conversation; artifacts carry the results.

`tasks.lua` owns this lifecycle; every in-flight task is canceled on
`VimLeavePre` so no agent is orphaned when the editor exits — the same
lifecycle hygiene as the MCP sessions in chapter 2.

## Fan-out: one agent, many peers (`fanout.lua`, `orchestrator.lua`)

The interesting case isn't one agent talking to one agent — it's one agent
**delegating to many**. The orchestrator fans a task out to multiple peer
agents (discovered via their cards), collects artifacts, and reconciles them.

This is where A2A stops being "a protocol" and starts being "an
architecture": the planner→coder→reviewer pipeline from the rose/phlow world
(chapter 6) is a special case of fan-out where the peers happen to be local.
A2A generalizes it to peers that are *anywhere* — another machine, another
framework, another organization.

## The UI and commands

`ui.lua` is a floating-window browser over agents and tasks — deliberately in
the same visual style as the MCP UI (`ai.mcp.ui`). One visual language for
both protocols, because the operator's mental model is one system: *my tools*
(MCP, vertical) and *my peers* (A2A, horizontal). Commands are registered by
`commands.lua`; `sdks.lua` wires the SDK drivers.

## MCP vs A2A, in code

| | MCP (ch. 2–4) | A2A (this chapter) |
|---|---|---|
| Direction | Vertical: agent → tools/data | Horizontal: agent → agent |
| Discovery | Registry file (curated, local) | Agent Cards (fetched, remote) |
| Trust | Vet metadata before context | Validate cards, verify signatures |
| Unit of work | Tool call (ms–s) | Task (s–min, long-running first-class) |
| Output | Tool result | Artifacts + messages |
| Transport | stdio (here) / Streamable HTTP | JSON-RPC over HTTP(S) |

## What this teaches

1. **Discovery is the hard part of distribution.** The task lifecycle is
   straightforward JSON-RPC; the interesting engineering is in cards:
   validation, bounds, signatures, scheme checks. Knowing *who* you're
   talking to is harder than talking.
2. **Long-running changes the protocol.** A2A's task model (submit, track,
   artifacts) exists because agent work takes minutes. Protocols designed
   for RPC-shaped work break on agent-shaped work — this is the design
   lesson worth internalizing.
3. **Compose, don't compete.** The system this was built for uses MCP for
   tools and A2A for delegation *simultaneously*. The protocols are layers;
   the architecture is the composition.
